## Known costs and doubts
- Explore's home (`home(table, found, shown)`) takes about 1.7 s on the phone and runs again whenever places or rows
  change, so every few seconds while places are first being read. Needs a cheaper query or a coarser trigger.
- Explore pages recompute on every library state change, each with a database read.
- Names are matched with SQLite's `lower()`, which is ASCII only (Kotlin's `lowercase()` isn't); only non-ASCII
  capitals differ.
- The map's sources filter passes "always show this day" entries as SQL parameters (SQLite's limit is 999).
- Each library change re-reads the noted photos and up to 2,000 photos screens asked for (`StoriesController.want`).

## Rules learned in this work (keep them)
- **The server is the owner's production server with their real data.** Never upload made-up or test files. Backup
  reads MediaStore only and `backupQueue` drops `MadeUpLibrary.isMadeUp` items.
- **Test on the emulator** (`Pixel_10_Pro`, `emulator-5554`), always with `adb -s emulator-5554`. Its Journal has the
  placeholder identity `emulator-test-no-key` (matches no certificate, so it stays Offline); never enroll it. Use the
  debug made-up library: `am start -S -n com.chencohensolution.journal/.MainActivity --ei madeUpLibrary 300000`
  (`0` turns it off). A test note "Old" was left on a made-up photo there.
- **The owner's phone** (SM_S931B, wireless adb): only when the owner asks. Check there is no call
  (`dumpsys telephony.registry`, mCallState=0) and, unless the owner says otherwise, no Journal backup running
  (ongoing notification `key=0|com.chencohensolution.journal|1001`). `adb install` of the ~350 MB APK drops over
  wireless adb: push it (`MSYS_NO_PATHCONV=1 adb -s <serial> push <apk> /data/local/tmp/journal.apk`, compare sizes),
  then `pm install -r` on the phone, then delete the copy. Without `MSYS_NO_PATHCONV=1` Git Bash rewrites the phone
  path and adb "succeeds" pushing elsewhere (that happened once; the owner said to leave that stray file alone).
  Starting the app can begin a backup; don't reinstall or force-stop over it.
- **Editing:** use the editor tools. Perl multi-line substitutions corrupted files on this Windows machine (the text
  landed at the top of the file); `python` hangs here.
- **SQLDelight:** named parameters are ordered by first appearance (pass them by name); a column `data` becomes
  `data_`; the parser rejects `NOT (CASE ...)` and `NOT column` (write `column = 0`). New tables need a migration
  `N.sqm` (latest `6.sqm`). Keep SQL inside the store classes (`LibraryTable`, `FeedTable`, `ServerMediaStore`,
  `StoredMediaLibrary`, `UploadLedger`).
- **Shared code:** `Dispatchers.IO` needs `import kotlinx.coroutines.IO`; no JVM-only APIs. Android compiles without
  noticing, so run `compileCommonMainKotlinMetadata` (only the four older errors above are expected).

- **Fix for both platforms:** Moments' rows of photos already gone stayed when a day was noted again while its rows
  were being made (seen on the simulator: 1,337 stale rows, Moments stopped paging). `feed_dirty` notings are
  numbered now; migration `7.sqm` (database version 8) adds the number and makes every row again once.
  `FeedDirtyRaceTest` covers it. More than 365 days noted (a large library read in, or one written while rows were
  made) make all rows at once, seconds instead of minutes window by window (`FeedTable.MANY_DAYS`).
- **iOS:** Private settings, sound recordings (Moments' bar, calls, voice messages, a recording's page, one AVPlayer
  over the mTLS loader), and backup of calls and recordings from Files folders with Free up space by groups
  (`IosSoundFolders`, FLAC with AVAudioFile, `IosSoundFoldersTest`).
- Tests: shared 270 on the JVM, 269 on the iOS simulator, all passing. ffmpeg was installed on the Mac (Homebrew) so
  the local test server reads sound recordings.

Doubt: on the emulator with 300,000 made-up photos, making every row at once reads all items in one query
(`FeedTable.items` over the whole range) and took about 4 minutes with the heap near 300 MB; a new database does the
same on first start. Window by window it took longer still. Built since (Oct 26, 2026): every row is made a span of
about 4,000 items at a time (`FeedTable.refreshAll`), 21 s instead of 212 s on the emulator, with the heap staying
near where it was instead of rising by about 120 MB (library-on-disk.md, phase 5a). Still seen there: on a new
database the first refresh waits minutes for the made-up library's write of 300,000 rows before it can start.

Left for iOS (docs/ios-todo.md): PhotoKit change tokens, Ogg/Opus playback, "Only on these Wi-Fi networks". Plan B
